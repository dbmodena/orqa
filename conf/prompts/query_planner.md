### DERIVED COLUMNS
A step often creates a column no table contains: an aggregate's result, a flag or bucket, a rank position, a renamed column. Declare each one in that step's `produces`, with what it was computed from:
- `produces`: `[{{"name": <new column>, "operation": <short label: "sum", "mean", "count", "flag", "bucket", "ratio", "year_extract", "rename", ...>, "sources": [<column it comes from>, ...]}}]`
- Write a source that is a real column of a table as `Alias.column` (e.g. `Table_0.amount`). Write a source an EARLIER step derived as its bare name (e.g. `total_spend`) — that column may itself come from several tables, so qualifying it would be wrong. Never guess an alias.
- `sources` may be empty ONLY for an operation that genuinely reads no column (`count`, `size`, `row_number`, `rank`, `literal`, `constant`). Every other operation must say what it was computed from.
- Wherever a step also declares an output in `params` (`output_column`, `new_column`, or the keys of `aggregations`), declare it in `produces` too — `params` carries the shape each op needs, `produces` carries the origin.

DECLARE ONCE. A derived column is declared only in the step that creates it. From that step onward it behaves exactly like a real column of the data: any later step may reference it by name in `columns` or `params` for any purpose — filtering, grouping, aggregating, sorting, ranking, joining, correlating, or as the origin of a further derived column. Never re-declare it in a later step, and never declare a name that a table already has.

### DATA QUALITY / CLEANING
Tables are shown RAW — no missing-token conversion, no number or date parsing, no null-row dropping. COLUMN STATISTICS describes every shown column; read it with this legend:
`Table_i: <rows> rows; <table fact>; ...`, then one line per column: `- name (type): fact; fact; ...`.
`v ×n` = value v in n rows; a bare count (`12 null`, `3 untrimmed`) counts rows; `blank` = empty or whitespace-only text, which is not NULL.
"..." = a text value exactly as stored (JSON-escaped): in SQL write it in single quotes, doubling any '. `"abc"…` = a longer stored value starting with abc (match with LIKE 'abc%' / .str.startswith). Unquoted values are numbers or booleans; dates appear as YYYY-MM-DD after the word `parsed`, and dates are UTC: `parsed a..b` is UTC, and the recipes give UTC; convert to a local zone only when the plan names it. `offsets +00:00 on every value` / `on n of m values` = how many of the ISO values carry a UTC offset.
`<k> values:` lists EVERY value; `1 value: v ×n` = v is the only stored value, the other rows are null or blank. `most common` lists only frequent ones; `+t more ×c each` = t more values with c rows each; `<k> distinct, each ×c` = every value in exactly c rows.
Shown numbers are stored values (compare non-whole floats with a tolerance, never ==), except: `quartiles` are rounded summaries; `a..b` (min..max), `far high` values and `all others <= x` are rounded outward past long decimals.
`(missing token)` / `missing tokens` = values matching the configured missing-value spellings; usually missing, but you decide (a "-" can be a real category).
`number text` casts to a number but may still be an identifier (ZIP, id, house number): cast only for arithmetic or numeric comparison. `date as number yyyymmdd` = whole numbers that are calendar dates (20200416): parse them, never add or average them.
`identifier:` = structural evidence that the column names records: never sum, average or correlate it, count its distinct values, join only on the same id space; a measure constant per category can read as one — judge by its name and values. `one row per x` in the header = each row is one x.
`filled down:` = a spreadsheet fill-down: a value holds for the blank rows below it until the next value — forward-fill it before grouping, filtering or counting per value; `(k once x is filled down)` on repeated rows = the repeats left after that fill.
Backticked text is a pattern or a literal fragment (an affix such as `%`), never a whole stored value: in `patterns` and `not ...` groups only `#` (a run of digits) is a placeholder and letters are literal; in `code shape` and `date-like text` shapes `9` = one digit and `a` = a run of letters.
An absent fact means nothing to report.

**The statistics detect; they never tell you whether what they found is noise or signal — that judgment is yours.** For every fact on a column your plan uses, ask what it MEANS, not how rare or oddly-shaped it is:
- An explicit non-answer/placeholder ("no data recorded", even when it is not a missing token) or a sentinel (a lone `-1`/`999`/`9999` far from the rest) → a `clean` step: `impute`/`drop_rows`/`drop_column`/`cast`. A value that is not a missing token goes in that action's `treat_as_missing` list, so the code generator treats it as missing too.
- A genuine, informative value — a censoring/top-coding convention (a bound recorded instead of a number), a qualitative label standing in for a range, or a rare-but-real extreme → discarding it is a loss. Add a `derive` step that PRESERVES it as its own queryable feature (`technique: "flag"` or `"bucket"`). This is often where the most interesting questions come from — the feature can legitimately be what the `question` is about.
- Rarity alone is never reason to clean something away, and a shape is never automatically dirty. An age column recording minors as `"<18"` is censored data, not corrupted — the move is an `is_minor` flag, not a `clean` step turning it into NaN. Treat any of it as noise only with a CONCRETE reason.

What each fact asks of a plan that uses the column:
- `null` and `blank` (empty or whitespace-only text) are missing values — except beside a single stored value (`1 value: v ×n`, e.g. a 1/blank flag), where null usually means "no": decide, and never drop those rows as missing.
- `untrimmed`, `case/space variants`: one value stored under several spellings — normalise it (trim, collapse spaces, lowercase) before any group, filter or join on the column.
- `filled down: k of n rows hold a value, each starting a block of blank rows`: a spreadsheet fill-down — the value holds for the blank rows below it until the next value. Forward-fill it BEFORE any group, filter or count per value: a `clean` step with `{{"column": <name>, "action": "impute", "strategy": "ffill"}}` (the code generator has the recipe); without it the blank rows fall out of every group.
- `number text`: cast with the shown format (copy the fact into the `cast` action's `format`; when it is `ambiguous` or `mixed`, decide the reading from the listed values, the TABLE SAMPLE rows and the metadata and write that reading instead, never the undecided fact: e.g. `thousands comma`, `decimal comma`, or for mixed which spellings use which decimal mark), and only for arithmetic or numeric comparison: number text can be an identifier. Its `not numbers` values: a comparison prefix (`<`, `>`, `≤`, `≥`) or a trailing `+` is a censored bound — flag/bucket it, never strip it to a number; a group that parses with another `.`, `,`, `'` or space separator is a second number format — parse it, do not drop it; `/` and `-` digit shapes (`#/#`, `#-#`) are compound codes, ranges or fractions — keep them as text unless the plan states their meaning. `<n> rows without the suffix/prefix` = values on another scale (0.855 beside 85%) — rescale or separate them before any arithmetic.
- `date text`: parse with the shown format (copy it into the `cast` action's `format`; for `(order unknown)`, decide day-first or month-first from the listed values, the TABLE SAMPLE rows and the metadata, and write the one format you chose, e.g. `%m/%d/%Y`) and scope periods with the `parsed` range, which is UTC like the parsed values the code produces (`, every month present` / `k of n months present` after it = which months of the span hold data: never scope a period the data does not cover). `time always 22:00` / `23:00` = likely local dates stored as UTC: the date is likely the next day. Likewise ISO timestamps with `offsets +00:00` whose `parsed` range starts at 22:00 or 23:00 are likely a local clock stored as UTC: convert them to local time (name the zone in the step) before deriving day, month, year or hour, or scoping a period.
- `date as number yyyymmdd`: whole numbers that are calendar dates (20200416) — a `cast` action to `datetime` with `format` `%Y%m%d` before any period scoping, date arithmetic or grouping by month or year; never sum or average them, and never compare them as numbers with a parsed date.
- `time text`: a time of day, not a date — cast it as a time with the shown format, never as a date.
- `digit code`: an identifier whose leading zeros matter — keep it as text, never cast it.
- `missing tokens` / `(missing token)`: usually missing, but a token can be a real category (a "-"/"+" sign flag) — decide, and say which in the step's `description`.
- `far high`: the values above a wide gap — a sentinel (99999, 999), a total row, another id space, or a genuine large record; decide which. `far high block` = a separate code/id range: keep its rows. Exclude or flag far-high rows with the shown bound (`col > x` for `all others <= x`), never by listing values.
- `repeated min` / `repeated max`: on a measure, a cap or default recorded at the boundary (hundreds of exact `90`s in an age column) — a genuine recorded bound: `flag`/`bucket` it, never discard it silently. On a code or id column it is just a frequent code.
- `<k> infinite`: rows stored as inf/-inf (often a division by zero upstream); range and quartiles leave them out, but any sum or mean over them is infinite — a `clean` step drops or flags them first.
- `identifier:` (its evidence follows: `record id (sequence ...)`, `unique in every row`, `unique in every distinct row`, `code of <text col>`, `part of the row key (...)`, `each value fixes <b>`): the column names records, not a quantity — never `sum`, `mean`, `bucket` or `correlate` it; to count entities count its distinct values (`unique in every distinct row` = the repeated rows are copies of one record). Join on it only when the other table carries the SAME id space — two files' record numbers are unrelated even when their ranges match. `code of x`: filter on the code, label with x. A measure that is constant per category (a pay scale per grade) also reads `each value fixes ...`: judge by the column's name and values. A bare `sequence` fact is the same record-number evidence.
- `geometry`: never group or sum it.
- Table facts (the header line):
  - `total row` / `total rows`: totals stored among the data rows — exclude them before any sum or count, using the shown handle (the label value, else the measure value). `(k of n rows) ... with the same (g)`: only k of the n marker rows are sums of their (g) group — exclude the marker rows of groups that have other rows; a marker row alone in its group is a record.
  - `fully empty rows` are not records; `rows repeat an earlier row`: double entries or genuine repeats — decide. `identical even in <col>` (a near-unique column) points to double entries; with `no column identifies rows` repeats are plausibly real events (a log of identical tickets) — never deduplicate them without a concrete reason. `(k once x is filled down)` / `(none once x is filled down)`: how many repeats survive the forward-fill of a `filled down` column — only those can be double entries.
  - `one row per x` / `one row per (a, b)`: each row is one x, or one (a, b) combination — to count entities, count distinct x (distinct (a, b)), not rows. `b numbered within a`: b restarts in every a, so b is an id only together with a — count (a, b) combinations, never distinct b alone.
  - `one-to-one: (a, b)`: one dimension stored twice (a code and its name) — filter on the code, label with the name. `except k rows`: those rows break the pairing — a cleaning target (often rows shifted by a broken CSV quote).
  - `each a has one b`: b is constant within each a, so a filter on b keeps or drops whole a groups, and a numeric b repeats on every row of its a — take it once per a (e.g. MAX(b) per a), then sum. `(+k more)`: k more such facts not shown.
  - `t = a + b`: t is the total of its parts — never add t to a or b.
- **DANGER — `far high` feeding a `sum`/"total":** never drop a far-high value from a column a later step SUMS unless you have a CONCRETE reason it is wrong (a sentinel, a total row, impossible for the domain, a duplicated-digit typo). The gap alone is never that reason — it flags rarity, not error. A real, unusually large payment/grant is exactly what a total must include; dropping it understates the true total, which is a wrong answer, not a cleaner one. Round, plausible numbers within the column's own unit (grants of $400k–$600k where typical is $100k) are genuine — keep them.
- **DANGER — `repeated min` / `repeated max` feeding a `mean`/`sum`:** the mirror failure. Silently including a capped value with no `flag`/`bucket` step marking which rows were capped misrepresents the result as if it reflected the true unbounded distribution (a capped ceiling biases a mean down, a capped floor up). Either preserve the cap as its own feature, or — when the question is honestly about the capped population as recorded — say so explicitly in `expected_result_description`.
- **DANGER — `correlate` against a column with no variance in this plan's scope:** if one correlated column is CONSTANT across the plan's grouping, the coefficient is mathematically UNDEFINED (NaN), not weak, and the query is rejected. The common trap: deriving "average year" from a table already scoped to a single fixed period — every row shares that year, so there is zero spread. Before adding a `correlate` step, check BOTH columns can plausibly vary across the grouping; if a fixed scope guarantees one side is constant, correlate against something that varies, or drop the step for a comparison that doesn't need variance on both sides (a ratio, or the two figures side by side).

A `clean` step's `params` follows the `{{"actions": [...]}}` convention on the step schema; cite the exact quoted values from COLUMN STATISTICS in the step's `description` — never invented ones, never a backticked shape. If a `clean` step touches a column a later `join`/`union` relies on, place it BEFORE that step.

### COMBINING METRICS ACROSS TABLES
When a plan blends figures from more than one table into a single output value (a `derive`/`aggregate` producing a "combined total" or blended score), the combination must be substantively meaningful. This does NOT apply to `correlate`: a coefficient is scale-invariant (normalized to [-1, 1] regardless of units), so correlating a COUNT against a dollar amount is sound and needs no unit reconciliation.
- NEVER sum, average, or blend raw values on incommensurate units/scales into one additive total (a COUNT of records + a SUM of an area + a SUM of a dollar amount) — the largest-magnitude term silently dominates. Compare the columns' `range` and `quartiles` in COLUMN STATISTICS: if magnitudes differ by orders of magnitude, or the business definition differs (count vs. measurement vs. money), report them as separate columns, combine via a dimensionally-sound rate/ratio/index ("complaints per action", "actions per square mile"), or normalize (z-score/min-max) if one blended index is genuinely the point.
- Combining figures over DIFFERENT periods isn't inherently wrong — a plan MAY compare, rank, or compute a ratio/trend BETWEEN periods when that comparison IS the insight. Not allowed: silently summing values from different periods into one undifferentiated total. Keep them as distinct, separately-labeled figures (or an explicit ratio/delta) in the steps and `expected_result_description`.
- Same-unit does NOT mean summable: plain counts from conceptually unrelated administrative processes (building-permit + parking-ticket + tree-planting counts) are as meaningless added as mismatched units. Ask whether the sum is one quantity a domain expert would recognize and name ("total complaints" across sub-categories of the SAME register is fine). A generic thematic label slapped on afterward ("combined civic activity") is a rationalization, not a shared referent.
- Sanity-check against a concrete row: if one term can be near-zero while the combined value barely changes because another dominates, the combination isn't meaningful — present the components separately or as a dimensionally-valid ratio.
