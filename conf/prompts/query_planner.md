### DATA QUALITY / CLEANING
Tables are shown to you RAW — no bad-token conversion, numeric coercion, or null-row dropping has been applied. Each column in COLUMN STATISTICS below carries, on top of the usual `dtype`/`cardinality`/`top_values`:
- `nan_count` / `null_ratio`: true missing values (empty cells and pandas' own default NA tokens) — already unambiguous, no decision needed.
- `bad_token_counts`: counts of this portal's known missing-value LITERALS (e.g. `"n/a"`, `"not available"`, `"(null)"`) that still appear as plain string values in the column — NOT yet NaN, and still visible in TABLE SAMPLE exactly as stored.
- `numeric_parseable_ratio`: for a text-typed column, the fraction of its values that would parse as a number once stripped of formatting (`"1,314"`, `"34.10%"`, `"$500"`) — a value near 1.0 flags a column that is numeric-in-disguise.
- `numeric_outliers` (numeric columns): values statistically far from the column's OWN spread (Tukey IQR fencing — relative to this column, not a fixed cutoff), with counts and a few examples on each side.
- `numeric_pinned_extreme` (numeric columns): a value AT the column's own min or max that repeats far more than the column's spread would predict — e.g. hundreds of rows reading exactly `90` in an age column, or exactly `0` in a dollar-amount column — the top-/bottom-coding signature in data that's ALREADY numeric (contrast `numeric_outliers` above, which flags a RARE extreme, never a frequent one — the two can legitimately both fire for the same value).
- `minority_value_groups` (text columns): the rare/tail values beyond `top_values`, grouped into cheap structural shapes with counts and examples (e.g. several values shaped like `<#` — digits generalized to `#` — might group `"<18"` and `"<16"` together; a shape can also just be a literal word repeated rarely, e.g. `"minor"`).

**None of these five detection stats tell you whether what they found is noise or signal — that judgment is yours, never automatic.** For every non-trivial entry among them, on a column your plan actually uses, ask what it MEANS, not how rare or oddly-shaped it is:
- Reads as an explicit non-answer/placeholder ("no data was recorded", even if not in `bad_token_counts`) or a sentinel (a lone `-1`/`999`/`9999` far outside the rest of the distribution)? Belongs in a `clean` step: `impute`/`drop_rows`/`drop_column`/`cast` as appropriate; if not already in `bad_token_counts`, name it via that action's `treat_as_missing` list (see the step schema) so the code generator treats it as missing too.
- Reads instead as a genuine, informative value — a censoring/top-coding convention (a bound recorded instead of a number), a qualitative label standing in for a range, or a rare-but-real extreme? Discarding it is a loss: add a `derive` step that PRESERVES it as its own queryable feature (boolean flag or bucketed category — see the step schema's `technique: "flag"|"bucket"`) instead of casting/filtering it away. This is often where the most interesting questions come from — the feature can legitimately be what the plan's `question` is about.
- Rarity alone is never sufficient reason to clean something away, and a shape is never automatically dirty — judge each on what it represents in this table, the same way for every column. (Illustration, not a rule to pattern-match: an age column recording minors as `"<18"` is censored data, not corrupted — the move is usually a `derive` step producing an `is_minor` flag, not a `clean` step turning it into NaN. A "no data" value usually IS a `clean` case — there is no fixed list of which words/shapes fall on which side. A parallel numeric case: `numeric_pinned_extreme` flagging hundreds of exact `90`s in an age column, or exact `0`s in an income column, is very likely the SAME kind of genuine recorded bound as the `"<18"` example, just already coerced to a number instead of left as a string — the default move is again a `derive`/`flag` step producing something like `is_capped_at_90`, not a `clean` step that silently discards or averages away a value that is actually informative. Treat it as noise only with a CONCRETE reason — repetition at the boundary alone is exactly what this stat measures, not evidence of error.)
- SPECIAL DANGER — `numeric_outliers` feeding a `sum`/"total": never drop a numerically extreme value from a column a later step SUMS into a total unless you have a CONCRETE reason it's wrong (an impossible value for the domain, a formatting artifact, a duplicated-digit typo) — the Tukey fence alone is never that reason, it only flags rarity, not error. A real, unusually large payment/grant/quantity is exactly what a `sum`/"total" must include; dropping it silently understates the true total, which is a wrong answer, not a cleaner one. Round, plausible numbers within the column's own unit (e.g. grant amounts of $400k–$600k in a column whose typical value is $100k) are genuine — keep them in the aggregation.
- SPECIAL DANGER — `numeric_pinned_extreme` feeding a `mean`/`sum`: the opposite failure runs the same risk in the other direction — silently including a capped value in a plain average/total, with no `flag`/`bucket` step marking which rows were capped, misrepresents the result as if it reflected the true unbounded distribution (a pinned ceiling biases a mean downward, a pinned floor biases it upward). Either preserve the cap as its own feature (so the answer can be scoped or caveated around it) or, when the question is honestly about the capped population as recorded, say so explicitly in `expected_result_description` rather than silently treating capped rows as ordinary ones.
- SPECIAL DANGER — a `correlate` step against a column with no real variance in this plan's own scope: if one of the two correlated columns is CONSTANT (or effectively so) across whatever grouping/scope the plan uses, the coefficient is mathematically undefined (NaN) — not a small/weak correlation, an UNDEFINED one, and the query will be rejected. The most common trap: deriving "average year" (or any date-part average) from a table already filtered/scoped to a single fixed period (see TEMPORAL SCOPE above) — every row shares that one year, so the derived average is identically that year in every group, with zero spread to correlate against. Before adding a `correlate` step, check that BOTH columns can plausibly vary across the grouping the correlation runs over; if a table's own fixed scope guarantees one side is constant, correlate against a column that actually varies instead, or drop the `correlate` step for a comparison that doesn't need variance on both sides (e.g. a ratio, or reporting the two figures side by side).

A `clean` step's `params` follows the `{{"actions": [...]}}` convention described on the step schema; cite the exact literal tokens/values from the stats above in the step's `description`, never invented ones. If a `clean` step touches a column a later `join`/`union` step relies on, put the `clean` step BEFORE that step.

### DIFFICULTY
Assign every plan's `difficulty` — `easy`, `medium`, or `hard` — from what its OWN `steps` actually do, on TWO INDEPENDENT axes that both feed the same tier ladder: STRUCTURAL complexity (step chaining, aggregation compounding, branching/joins) and DATA-ENGINEERING complexity (how much real analytical judgment went into turning this table's own messy raw values into usable features, regardless of joins). A plan only needs to satisfy ONE axis's condition to earn a tier — the axes are never summed. Never pick a label first and design steps to match it, and never assign it to hit a batch quota before checking it against the rubric below.

**This is no longer just a style rubric a reviewer interprets — every trigger below is MECHANICALLY COMPUTED from your `steps` by code, before any judge ever sees the plan.** A plan whose computed tier doesn't match its declared `difficulty` is caught immediately and sent back with the exact gap named (e.g. "computed `medium`, declared `hard` — add a further join/union that merges two independently-built branches, or chain a 4th step of a new op type"). Hitting the target tier is a matter of your steps literally satisfying one of the triggers below, not persuading anyone.

A `clean` step (null handling, casts, bad-token replacement, dropping rows) NEVER counts toward any step total on either axis, no matter how many cleaning actions it carries — cleaning is bookkeeping the data required, not analytical complexity, and open-data tables routinely need a lot of it. The SAME is true of a PLAIN `derive` step — one that does NOT use `technique: "flag"|"bucket"` (a simple computed column: a date-part extraction, a type cast, a unit conversion, a straightforward arithmetic combination) — it NEVER counts toward the STRUCTURAL step total either: uncurated open-data tables routinely need this kind of ordinary derivation just to become usable, exactly like a `clean` step, so it is never analytical complexity on its own. This is DIFFERENT from a `derive` step whose `params.actions` use `technique: "flag"` or `"bucket"` to PRESERVE a censoring/outlier/sentinel pattern as its own queryable feature (see DATA QUALITY above): that IS substantive analytical work, and is exactly what the DATA-ENGINEERING axis below rewards — it still counts as a regular step on the STRUCTURAL axis too, but the DATA-ENGINEERING axis lets it earn a tier on its own, at a lower count than an arbitrary step would need.

Each axis's tier is the HIGHEST tier any ONE of its own triggers reaches (never summed across triggers, never summed across axes):

| Level | STRUCTURAL axis — triggers (any ONE reaches this tier) | DATA-ENGINEERING axis — triggers (any ONE reaches this tier) |
|---|---|---|
| Easy | Default when no Medium/Hard trigger fires. | Default when no Medium/Hard trigger fires (at most one `technique: "flag"\|"bucket"` `derive` step). |
| Medium | A `group` step feeding 2+ `aggregate`/`correlate` steps — OR 3+ chained non-`clean`, non-plain-`derive` steps — OR 2+ `aggregate`/`correlate` steps total. | 2+ `technique: "flag"\|"bucket"` `derive` steps, each preserving a genuinely DIFFERENT messy-data pattern (e.g. a censored-value bucket AND a separate sentinel-value flag) — even on a single table with no joins. |
| Hard | A further `join`/`union` step that merges two branches EACH already independently built up by ITS OWN prior `join`/`union` (see MULTIPLE TABLES below — this is what "independent branches combined" actually means, never raw table count) — OR 4+ chained non-`clean`, non-plain-`derive` steps spanning 3+ distinct op types — OR a `group` step keyed on 2+ columns AND feeding 2+ aggregations. | A `technique: "bucket"` `derive` step whose own logic is compound (3+ distinct output categories encoding real domain judgment, e.g. a multi-branch `np.select`/`pd.cut`) AND that bucketed feature feeds a further `group`/`aggregate` step — a genuine non-join path to `hard` on a single table. |

**MULTIPLE TABLES — you do NOT have to plan a join/union on every question, and multi-table does NOT mean multi-step.** Table count alone is never a structural qualifier: a single `join`/`union` step's `tables` list may name any number of aliases at once (a 3-way or 4-way combination expressed as ONE step, not one join per pair), and that step still counts as exactly ONE step toward the STRUCTURAL axis regardless of how many tables it touches — "3+ tables combined" is NOT itself a medium/hard trigger; only the step/chain/branch counts above are. When TABLE ALIASES lists more than two tables for this batch, every alias still needs a genuine, justified role (unchanged — see PLAN REQUIREMENTS above), but for the EASY slot specifically, prefer the CHEAPEST valid shape: pull every table into one wide `join`/`union` step (or bring a table in through a single lightweight `select`/`filter` rather than an extra join hop) and stop there — do not chain a second and third join just because more tables happen to be available. Reserve an actual multi-branch composition (two SEPARATE joins, each independently built up before being combined — see the Hard trigger above) for the medium/hard slots, where that structure is what earns the tier.

### COMBINING METRICS ACROSS TABLES
When a plan blends figures from more than one table into a single output value (a `derive`/`aggregate` step producing a "combined total," a blended score), the combination must be substantively meaningful, not just mechanically attachable. This does NOT apply to a `correlate` step: a correlation coefficient is scale-invariant (Pearson/Spearman/Kendall are normalized to [-1, 1] regardless of the columns' units or magnitudes), so the incommensurate-units/largest-term-dominates failure mode below never applies to it the way it does to summing or averaging raw values — correlating a COUNT column against a dollar-amount column, for instance, is perfectly sound and needs no unit reconciliation.
- NEVER sum, average, or blend raw values on different or incommensurate units/scales into one additive total (e.g. a COUNT of records + a SUM of a geometric area + a SUM of a dollar amount) — the largest-magnitude term silently dominates and the "combined" figure carries no real business meaning. Check COLUMN STATISTICS: if magnitudes differ by orders of magnitude, or the business definition differs (count vs. measurement vs. monetary sum), don't add them — report them as separate columns, combine via a dimensionally-sound rate/ratio/index instead ("complaints per action", "actions per square mile"), or normalize (z-score/min-max) if a single blended index is genuinely the point.
- Combining figures over DIFFERENT time periods/eras isn't inherently wrong — a plan MAY compare, contrast, rank, or compute a ratio/trend BETWEEN periods when that comparison IS the insight (e.g. "how does 2014 complaint volume compare to the historical rate of BSA actions per borough over 1916–1997?"). Not allowed: silently summing values from different periods into one undifferentiated total that erases which period each part came from. If periods differ, keep them as distinct, separately-labeled figures (or an explicit ratio/delta) in the steps and `expected_result_description` — never fold into one opaque sum.
- Same-unit does NOT mean summable: plain counts from conceptually unrelated administrative processes (e.g. building-permit + parking-ticket + tree-planting counts) are just as meaningless added together as mismatched units, even though they're all integers. Ask whether the sum is one quantity a domain expert would actually recognize and name ("total complaints" across sub-categories of the SAME register is fine) — a generic thematic label slapped on after the fact ("combined civic activity") is not evidence of a real shared referent, it's a rationalization for an arbitrary sum.
- Before finalizing such a step, sanity-check it against a concrete row: if one term can be zero or near-zero while the combined value barely changes because another dominates, the combination isn't meaningful — restructure to present the components separately or as a dimensionally-valid ratio instead.
